CASE STUDY / AI PRODUCT

Noonshow

A high-performance, phonetic-aware semantic search engine for movie discovery.

Visit Noonshow ↗ Back to portfolio

System architecture

Executive summary

Searching Indian cinema is challenging when people remember plot details rather than titles, or spell artist names phonetically in several different ways. Noonshow is designed as an intelligent, multi-stage hybrid search engine that returns relevant results quickly while handling both cases.

The backend combines an asynchronous FastAPI gateway, dense-vector search, cross-encoder reranking, Redis caching, spaCy NLP and live progress streaming. Each responsibility is kept in a decoupled module so the service can remain responsive while performing heavier ML work.

Dual-track query understanding

A query such as “movies directed by Mani Ratnam with A.R. Rahman music set in the 90s” contains metadata filters and semantic context. The NLP layer separates technical anchors such as director, music and cast from the plot description. A custom phonetic resolver maps spelling variants of Indian cinema names to canonical entities, allowing those resolved IDs to become precise metadata filters before vector retrieval.

Example query decomposition

“Kamal Haasan movie where hero acts as an old grandmother”
Technical intent: actor = Kamal Haasan. Plot intent: hero acts as an old grandmother.

Multi-stage retrieval and reranking

Dense embeddings provide broad recall over movie plots and synopses, while metadata constraints reduce the candidate pool. The highest-ranked candidates are then sent to an isolated cross-encoder reranking service, which scores complete query-document pairs for sharper semantic precision. A score floor removes weak matches; an asyncio semaphore throttles concurrency to protect the embedding workers under load.

Streaming, enrichment and trending

Server-Sent Events stream search stages to the client as they happen—query parsing, retrieval, reranking, enrichment and completion—so the experience feels responsive rather than waiting on one final payload. Redis caches external movie metadata for seven days, while an asynchronous fetcher enriches results on cache misses and local SQLite data provides a fallback.

Trending results use interaction-weighted, four-hour Redis buckets with exponential decay over a 24-hour window. Recent clicks carry more weight than impressions, and curated classics keep the UI useful when traffic is sparse.

Feedback and observability

Each search receives a unique identifier, linking user feedback to the result set that produced it and creating a useful dataset for evaluating and improving ranking. Prometheus latency histograms, OpenTelemetry traces and structured logs provide visibility across embedding, retrieval, reranking and metadata-fetch stages.

Engineering lessons

  • Isolating the reranker keeps ML compute spikes from blocking the API event loop.
  • Streaming progress improves perceived responsiveness, even for short searches.
  • Domain-specific phonetics materially improve metadata precision in regional datasets.
  • Long-lived metadata caching reduces dependency on third-party APIs and network latency.

What’s next

The next areas of exploration are hybrid sparse-dense retrieval—combining BM25 keyword scoring with dense vectors—and using attributed user feedback to evaluate and refine reranker performance over time.
